# Roxy Browser 数据同步逻辑

> 面向新人的说明文档。读完这份文档,你应该能回答:同步的是什么数据、什么时候同步、走哪些通道、失败了会怎样。

> - `apps/electron/src/utils/oss.ts`

## 1. 一句话概览

每个浏览器窗口(profile)产生的数据,通过**两条独立通道**同步到云端:

| 通道 | 同步内容 | 载体 | 入口方法 |
|------|----------|------|----------|
| **OSS 上传** | 浏览器本地缓存文件(IndexedDB、LocalStorage、书签、历史、扩展数据等),打包成 `browser-cache.zip` | 阿里云 OSS 对象存储 | `uploadData()` 内的 `aliOSS.putStream()` |
| **API 上传** | 窗口元数据(cookie、打开的网址、插件登录态 lumiLogin、OSS 版本号、打开状态) | 后端接口 `user_mdf_window_sync_v2` | `syncWindowData()` → `userMdfWindowSyncV2Create()` |

关键结论(后面会逐条展开):

1. **OSS 和 API 不是简单的"并行两件事"**,而是有先后:先做 OSS 上传(每个窗口各自做,窗口之间并行),全部结束后再批量做 API 上传。
2. **绝大部分数据只在窗口"关闭"时才同步**。运行过程中只做两件轻量的事:把 cookie 读进内存、定时上报"窗口在线状态"。
3. **OSS 上传失败不会重试,也不会阻断 API 上传**;cookie / 网址 / lumiLogin 这些元数据仍会通过 API 正常同步,只是缓存 zip 这一轮不更新。
4. **API 上传失败会重试**(普通关闭重试 1 次,退出/升级/登出场景重试 3 次),最终失败只记日志,不阻断流程。

## 2. 同步的具体数据

### 2.1 OSS 通道:本地缓存文件

要打包进 zip 的文件由窗口配置里勾选的同步项决定,映射关系见 `getNeedSyncLocalFileMap()`(`constants.ts`)。Chrome 内核为例:

| 配置项 | 对应文件/目录 |
|--------|---------------|
| `syncIndexedDb` | `/Default/IndexedDB` |
| `syncLocalStorage` | `/Default/Local Storage` |
| `syncBookmark` | `/Default/Bookmarks` |
| `syncHistory` | `/Default/History` |
| `syncSessionStorage` | `/Default/sessionstorage.sqlite` |
| `syncExtensions` | `/Default/Local Extension Settings` 等扩展数据目录 |

> Firefox 内核的文件路径不同(如 `places.sqlite`、`storage/default`),但逻辑一致。

这些文件被压缩为 `browser-cache.zip`,上传到该窗口在 OSS 上的固定路径 `${ossDirPath}browser-cache.zip`。

> ⚠️ 注意:**cookie 不在 OSS 通道里**。Chrome 的 cookie 数据库是加密的(Windows DPAPI),直接打包没用,所以 cookie 走 API 通道(明文 JSON)。

### 2.2 API 通道:窗口元数据

`uploadData()` 在 `finally` 里组装出 `uploadParams`(`browserItem.ts`):

```ts
const uploadParams = {
  id,                                  // 窗口 id
  cookie,                              // syncCookie 开启时,内存里的 cookie 序列化为 JSON
  defaultOpenUrl,                      // 关闭时浏览器打开着的标签页(下次启动恢复)
  lumiLogin,                           // 插件登录态(<1MB 才同步)
  syncValue: { version, fileCount },   // OSS 缓存版本号 + 文件数(供下次启动判断是否需要下载)
  openStatus: false,                   // 标记窗口已关闭
}
```

## 3. 关键角色

| 角色 | 职责 |
|------|------|
| `BrowserItem` | 单个浏览器实例。持有 `uploadData()`(组装数据 + OSS 上传)、`close()`、`handleOnDisconnected()`(进程关闭回调) |
| `AfterLaunchTask` | 启动后任务。负责运行时把 cookie 读进内存(`this.cookies`)、`saveCookiesNow()`、`getUploadData()` 收集元数据 |
| `BrowserManager` | 全局管理器。负责批量关闭(`closeAll`/`batchClose`)、聚合所有窗口的上传参数、调用 `syncWindowData()` 走 API |
| `aliOSS` | 阿里云 OSS 客户端封装(`oss.ts`),每次调用前自动用后端接口换取 STS 临时凭证 |

## 4. 什么时候同步?(回答:运行中同步吗?)

### 4.1 运行过程中 —— 只做轻量同步

运行时**不上传 OSS,也不做完整的元数据 API 同步**。只有两类轻量动作:

1. **cookie 读进内存(不上传)**
   `afterLaunchTask` 在开启 `syncCookie` 时,通过定时器(每 3 秒)、标签页事件(`targetchanged`/`targetcreated`/`targetdestroyed`)、网络响应监听,持续把最新 cookie 用 CDP `Storage.getCookies()` 读到内存变量 `this.cookies`。
   **这一步只是"缓存到内存",不发任何网络请求。** 真正上传发生在关闭时。

2. **窗口在线状态上报**
   - 启动时:`syncWindowOpenStatus`(防抖 3 秒)调 `userMdfWindowSyncV2Create` 上报 `openStatus: true`。
   - 运行中:`reportWindowOpenStatus` 每 5 分钟调 `userModifyWindowReportTimeCreate` 上报一次"还活着"。
   这些只同步**在线状态**,不涉及 cookie / 缓存文件 / 网址等业务数据。

> **为什么不在运行中持续上传?**
> 缓存文件(IndexedDB、扩展数据等)体积大且频繁变化,运行中持续打包上传成本太高;而且浏览器还开着时文件可能被占用/写到一半。所以设计成"关闭时一次性快照上传"。

### 4.2 窗口关闭时 —— 完整同步

无论是用户手动点 X 关窗,还是 App 退出/升级/登出触发的批量关闭,都会触发完整同步。这是数据同步的主战场,详见下一节。

## 5. 关闭时的完整同步流程

### 5.1 时序图

```mermaid
sequenceDiagram
    participant U as 用户/系统
    participant BM as BrowserManager
    participant BI as BrowserItem
    participant ALT as AfterLaunchTask
    participant OSS as 阿里云 OSS
    participant API as 后端 API

    U->>BM: 关闭(单窗口 / closeAll)
    BM->>BI: close(dirId)
    Note over BI: Chrome 先 saveCookiesNow()<br/>(CDP 读 cookie 进内存)
    BI->>BI: browser.close() 关闭浏览器进程
    BI-->>BI: 进程关闭触发 handleOnDisconnected
    Note over BI: Firefox 在此处 saveCookiesNow()<br/>(读 cookies.sqlite)
    BI->>BI: uploadData()

    rect rgb(235,245,255)
    Note over BI,OSS: 第一阶段:OSS 上传(每个窗口各自做)
    BI->>ALT: getUploadData() 收集 cookie/网址/lumiLogin
    BI->>BI: 压缩 needSyncFiles → browser-cache.zip
    BI->>OSS: aliOSS.putStream() 上传 zip
    OSS-->>BI: 成功→version+1 / 失败→catch 吞掉
    BI-->>BM: 返回 { requestHeaders, uploadParams }
    end

    rect rgb(235,255,235)
    Note over BM,API: 第二阶段:API 上传(跨窗口批量)
    BM->>BM: 等所有窗口 uploadData 完成(allSettled)
    BM->>BM: 按 requestHeaders 分组
    BM->>API: syncWindowData() 分批调 user_mdf_window_sync_v2
    API-->>BM: 成功 / 失败重试
    end
```

### 5.2 文字版分解

**第 0 步:保存 cookie 到内存**
- Chrome:在 `close()` 里、关闭浏览器**之前**调 `saveCookiesNow()`(用 CDP `Storage.getCookies()`)。因为 CDP 连接一断就读不到了。
- Firefox:在 `handleOnDisconnected` 里、进程关闭**之后**读 `cookies.sqlite`(进程不退出会锁库)。

**第 1 步:`uploadData()` —— OSS 上传(单窗口)**
1. `getUploadData()` 收集 cookie(内存里的)、`defaultOpenUrl`、`lumiLogin`。
2. 把 `needSyncFiles` 压缩成 `browser-cache.zip`。
3. `aliOSS.putStream()` 上传到 OSS。成功则 `version + 1` 并写本地版本文件。
4. **无论上传成功与否**,在 `finally` 里组装 `uploadParams` 并返回 `{ requestHeaders, uploadParams }`。

**第 2 步:`#batchUploadData()` + `syncWindowData()` —— API 上传(跨窗口批量)**
1. `BrowserManager` 收集所有正在关闭窗口的 `uploadData()` Promise,用 `Promise.allSettled` 等它们全部结束。
2. 按 `requestHeaders`(token + workspaceId)分组——不同账号/工作区的数据要用不同请求头。
3. 每组调 `syncWindowData()`,内部再切成小批次(普通 10 个/批,退出场景 6 个/批)调 `user_mdf_window_sync_v2`。

## 6. OSS 和 API 是并行/异步的吗?(回答 Q2)

**要分两个层面看:**

### 6.1 同一个窗口内:OSS 在前,API 在后(串行)

单个窗口的 `uploadData()` 会先 `await` 完 OSS 上传,才返回 `uploadParams`;而 API 上传发生在更后面的 `syncWindowData()`。所以对一个窗口而言:**先 OSS,后 API,是串行的**。

### 6.2 多个窗口之间:OSS 上传彼此并行

`closeAll` / `batchClose` 会把所有窗口的关闭 Promise 丢进 `Promise.allSettled` 一起跑,所以**多个窗口的 OSS 上传是并行的**。

### 6.3 阶段之间:OSS 阶段整体先于 API 阶段

`BrowserManager` 必须等**所有窗口的 `uploadData()`(含 OSS 上传)都 settle 之后**,才开始分组做 API 同步。所以整体节奏是:

```
[窗口A OSS] ┐
[窗口B OSS] ├─ 全部并行,全部结束后 ──→ [批量 API 同步]
[窗口C OSS] ┘
```

> 一句话:**窗口之间 OSS 并行;OSS 阶段结束后才统一走 API。两者不是"同时发起的两个独立请求"。**

## 7. OSS 上传失败了会怎样?(回答 Q3)

看 `uploadData()` 的 `try/catch/finally` 结构:

```ts
let newVersion = syncValue?.version || 1
let isUploadSuccess = false
try {
  // 压缩 + aliOSS.putStream()
  newVersion = newVersion + 1   // ← 只有上传成功才 +1
  isUploadSuccess = true
} catch (error) {
  console.log('uploadData error: ', error)   // ← 失败只打日志,不抛出、不重试
} finally {
  const uploadParams = {
    cookie, defaultOpenUrl, lumiLogin,        // ← 这些与 OSS 无关,照常带上
    syncValue: {
      version: newVersion,                    // 失败时仍是旧版本号(没 +1)
      fileCount: isUploadSuccess ? needSyncFiles.length : syncValue?.fileCount,
    },
  }
  return { requestHeaders, uploadParams }     // ← 失败也照常返回,API 阶段继续
}
```

逐条回答:

| 问题 | 答案 |
|------|------|
| OSS 失败会重试吗? | **不会**。`uploadData` 里 `putStream` 失败直接被 `catch` 吞掉,没有重试循环。(`aliOSS` 代理层对同步异常有一次重试,但对 `putStream` 这种异步 Promise 不生效。) |
| OSS 失败会阻断 API 上传吗? | **不会**。`finally` 仍返回 `uploadParams`,后续 API 同步照常进行。 |
| OSS 失败,cookie/网址会丢吗? | **不会丢**。cookie、`defaultOpenUrl`、`lumiLogin` 走的是 API 通道,与 OSS 是否成功无关,仍会同步。 |
| OSS 失败的影响是什么? | 只影响"缓存文件 zip"这一轮不更新:`version` 不递增,服务端继续指向上一份 OSS 缓存。下次关闭时会再尝试上传。 |

> 总结:OSS 失败是"**降级**"而非"中断"——这一轮缓存文件没更新,但元数据照常同步,数据不会因为一次 OSS 失败而整体丢失。

## 8. API 上传失败了会怎样?

看 `#syncWindowDataBatch()`(`browserManager.ts`),它**带重试**:

| 场景 | 批次大小 | 单次超时 | 最大重试次数 |
|------|----------|----------|--------------|
| 普通关闭 | 10 / 批 | 15 秒 | 1(即不重试) |
| 退出 / 升级 / 登出 | 6 / 批 | 45 秒 | 3 |

- 重试之间有递增退避:`setTimeout(2000 * attempt)`(第 1 次失败等 2s,第 2 次等 4s)。
- 用 `Promise.allSettled` 跑各分组,**单组失败不影响其他组**。
- 最终仍失败:打 `console.warn` 日志,返回 0(计入"未同步"),**不阻断退出**。
- 退出场景结束后会打印汇总:`Quit sync summary: closed X/Y, API synced M/N`,便于排查。

## 9. 退出 / 升级 / 登出的特殊处理

这三种场景通过 `closeAll({ ensureServerSync: true })` 进入,与普通关窗相比有几点强化:

1. **更保守的同步参数**:更小批次(6)、更长超时(45s)、更多重试(3 次),尽量保证退出前把数据同步上去。
2. **全屏进度 UI**:展示"正在关闭窗口 / 正在同步缓存"的进度,并提示用户**不要强制结束 App**。
3. **统一由 `closeAll` 触发同步**:退出期间各窗口的 `onCloseHandler` 不再各自触发上传(`if (!this.#ensureServerSync)`),避免重复同步导致进度计数越界。
4. **整体兜底超时**:`closeAll` 用 `Promise.race` 给整批同步加了一个上限(`60s + 每窗口 8s`,封顶 5 分钟)。万一个别窗口僵死,超时后放行退出,底层同步仍在后台继续跑,不会无限卡住退出流程。

入口集中在 `quitCleanup.ts` 的 `syncBrowserDataBeforeQuit()`,它是幂等可重入的:无论退出、升级还是登出,都先同步完数据再真正退出。

> 例外:**被踢下线(405)不做同步**。因为此时 token 已失效,没有权限上传,强行同步只会报错。

## 10. 常见疑问 FAQ

**Q: cookie 是实时上传的吗?**
A: 不是。运行中 cookie 只被读进内存(每 3 秒/事件触发),关闭窗口时才随 API 一起上传。

**Q: 我开着浏览器一直不关,数据会同步吗?**
A: 业务数据(cookie/缓存/网址)不会;只有"在线状态"每 5 分钟上报一次。要落库必须关闭窗口。

**Q: OSS 挂了,我的账号登录态(cookie)会丢吗?**
A: 不会。cookie 走 API 通道,与 OSS 独立。

**Q: 同步失败了用户会知道吗?**
A: 普通关闭失败只在日志里;退出/升级/登出有进度 UI,且有汇总日志 `Quit sync summary`。

**Q: 为什么 cookie 不打包进 OSS 的 zip?**
A: Chrome 的 cookie 库被 DPAPI 加密,换台机器解不开;所以读成明文 JSON 走 API 同步。
